## Exact operational workflow to preserve

1. Original application: establish authenticated company/branch/terminal and staff context. The independent preview supplies an explicitly labelled, fictional manager context and open mock cashier shift; it is not an authentication alternative for the real app.
2. Welcome → Start order → choose dine-in or takeaway. Dine-in requires selecting an available/occupied table and Continue. Opening an unpaid occupied table leads to order detail, then Add items or payment.
3. Browse/search categories → configure product (required options are initially selected) → add to draft. Edit quantities, notes, modifiers and service mode, or remove draft items. Previous batches remain visible but immutable.
4. Review cart → final order review. Dine-in: Confirm and send → status. Takeaway: Continue to payment; nothing enters kitchen until full settlement. Packaging uses existing CUP_LID / PAPER_BAG / TAKEAWAY_BOX / CUTLERY / STRAW / SAUCE / NAPKIN values.
5. Kitchen: start each pending batch → mark ready → serving screen marks ready work served/collected. Add-ons append batches.
6. Bill/detail → payment or split bill. Confirm each payment separately; insufficient tender, overpayment, missing QR provider, unsent dine-in drafts and unacknowledged active kitchen work block payment. The Complete order action follows settlement and shows a receipt; kitchen fulfillment may still be pending.
7. Fulfilled and paid dine-in order → DIRTY table → start cleaning → complete cleaning → available. Early payment does not release the table.

## Known source inconsistencies and limits

- Latest completion migration introduces DIRTY, while `types/table.ts` and portions of table management still describe the older CLEANING transition. The preview follows the latest database lifecycle and exposes both cleaning steps; the original files are untouched.
- Packaging props exist in `ReviewOrderScreen` but the current `App.jsx` does not forward them. Preview uses the already-existing packaging controls and codes; original wiring is untouched.
- Sample migration `20260822040000_seed_staging_catalog_sample.sql` supplies Nasi Lemak at RM 9.90 and the required SINGLE Spice Level / Mild option at no extra cost. Other checked-in demo references include Chicken Chop, Chicken Burger, French Fries, Lemon Tea, Test Coffee. Preview records use these names and structures; unspecified prices/table assignments are fictional fixtures, not claims about the installed catalog.
- No mock tax percentage, service fee, promotion or voucher discount will be invented. Voucher fixtures are empty and unsupported codes return a clear validation message. Cash and a fictional manual QR provider simulate only the existing payment methods.
- Reports and cashier operations are represented locally. Administration/configuration, auth/PIN and device setup are outside this operational redesign and remain in the original app. Real reports, export pipelines, RLS, payment providers, receipt printers, concurrency and permission enforcement cannot be validated by frontend mocks.

## Isolation plan

Register only `/pos/preview` (and its trailing-slash equivalent) in `src/main.jsx` before importing the original app. Dynamically load the original app and global CSS only for other paths. Keep all preview UI, fixtures, adapter, calculations, state and styles in `src/preview`; use no production hooks, repositories, Supabase clients, storage keys or auth providers. State lives in memory and resets on refresh. No deployments, migrations, endpoints, permissions or original POS components are changed.

Implementation specification, adapter contract and validation evidence are in the companion README and VALIDATION documents.
